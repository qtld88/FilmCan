# Phone notifications by QR code

**Date:** 2026-11-11 · **Lot:** 1 · **Branch:** `qt1/phone-qr`

## Goal

Getting backup notifications on a phone today means reading five lines of instructions and filling a URL, a token and two templates. Make it one switch and one scan, with no account, while keeping the full form for people who run their own ntfy topic or server.

## Expected behaviour

Settings › Push has two modes in the same page.

**Simple (default).** One switch, "Send notifications to my phone". When on, FilmCan creates a channel: the ntfy topic `filmcan-` + 32 random hex characters (128 bits from `SecRandomCopyBytes`) on `https://ntfy.sh`. The page shows a QR code, the channel name (selectable, with a copy button), "Send a test" and "New code…" (asks for confirmation: subscribed phones stop receiving). No token is ever sent to a generated channel.

**Advanced (folded).** The existing form, unchanged: "Use my own ntfy server or topic", topic URL, token, title and message templates. The templates apply in both modes.

**Which mode.** An explicit choice is stored in the preference `ntfyUseCustomServer`. When that preference is absent: custom if a topic URL is already filled, simple otherwise. So someone who configured a topic URL before this change keeps sending to it, with the token, and sees Advanced open; no preference of theirs is rewritten.

**Where the topic lives.** Preference `phonePushTopic` (not the keychain). It therefore survives app updates, unlike the keychain token.

**QR target.** `https://www.filmcan.eu/phone/#<topic>`. The page (`website/phone/index.html`) is static and self-contained: no third-party script, no analytics, no web font, `referrer: no-referrer`, `noindex`. The topic is in the URL fragment, which browsers do not send to servers; the page reads it locally, accepts only `[A-Za-z0-9_-]{1,64}`, and writes it with `textContent`. It shows two steps (install ntfy, subscribe) plus a "check it works" step, in English, French, German and Spanish, picked from the phone's language with a manual switch. Subscribing is offered two ways: copy the channel name and paste it in the app, or an "Open in ntfy" link (`ntfy://ntfy.sh/<topic>`).

**Sending.** `PhonePush.target` resolves the destination once, in `TransferViewModel.makeNotificationSettings`: the generated topic URL without token, or the user's URL with token. `NotificationDispatcher` reads the keychain only when the target wants the token.

## Edge cases

- Switch already on but nothing set up (older preferences with an empty topic URL), or a malformed stored topic: nothing is sent, as today. Settings › Push shows a "Create my QR code" button; a channel is only ever created by a click (the switch, that button, or "New code"), never by opening the page.
- Site unreachable or page not yet published: the channel name is on screen in the app; subscribing by hand works.
- ntfy.sh rate limit: the test reports "HTTP 429" with a plain sentence.
- Switching Advanced › own server off and on keeps the URL and token.

## What does not change

- Topic URL, token, templates and webhook settings of an existing user; keychain handling; signing.
- The engine, history, macOS notifications, webhook payloads.
- `NotificationSettings` call sites: the new field has a default.

## Not verifiable from the build environment

- The ntfy documentation could not be reached, so the deep-link format, iOS support for it and the public server's rate limits are from memory. The design does not depend on them: the copy-and-paste path needs none of it. Listed for the owner in the PR.

## Success criteria

- First click to test notification received in under 2 minutes on a phone without ntfy (manual).
- The generated topic has at least 128 random bits (unit test).
- Simple mode keeps working after an app update with no action (topic in preferences; manual check).
- Old preferences resolve to the same target as before (unit test).
